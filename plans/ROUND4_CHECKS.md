## 1. Gemini 7.1: E7 bootstrap RNG and the 3.5176 vs 3.5541 drift
**Answer: the E7 bootstrap is seeded deterministically and does not inherit global or mutated RNG state. The drift is a numpy-version difference in the simulated WALKS at the last two time points, not an E7 defect.**
- Static: `make_box` / `boot_means` use only the `rng` passed in (`rngs[7]`, a child of `SeedSequence([22, id, 2000+ds]).spawn(9)`); no `np.random.*` global, no unseeded `default_rng()`, no set/dict-order dependence (grep clean).
- Cell ring L=128 wpn 32, dataset 0 (REPRO_CHECK 9b cell). `run_dataset` twice in one process: identical (c_box 3.517622545358127, n_boot 15). `make_box` isolated, after `np.random.seed(0)`, after `np.random.seed(1)`, and after the other estimators have run: all four bit-identical (T-vector hash 39b9790a18498f05). `rngs[7]` state before the bootstrap: 200276163162311100741570999383501810338.
- First 5 bootstrap index arrays (multinomial block-count vectors, first 12 entries of row 0: 2,0,3,3,1,0,0,0,1,0,4,2; row hashes 0747968b5eef, 50124a057930, 2099fd642625, 311a4489e723, 6b59b45614dc) and first 5 studentised maxima (1.6468, 2.0443, 1.4251, 2.3925, **1.8436**) are identical on every run in numpy 2.5.5.
- **Cause.** My near-tie prediction (a point at count 30 flipping under float rounding) FAILED: no point within 1e-4 of 30, float and integer rules agree. Instead the integer return counts differ at the last two grid points between numpy versions: 2.5.5 gives (…45, 41, 28), numpy 2.4.6 gives (…45, 36, 34). Under 2.5.5 the last point has 28 < 30, so it falls to Clopper-Pearson (n_boot 15, n_cp 1); under 2.4.6 it is 34 >= 30, so it joins the bootstrap max-t (n_boot 16, n_cp 0), which raises the max. The bootstrap index arrays are identical across the two versions (same hashes), the 5th studentised maximum is 1.8436 vs 1.9550 and **c_box is 3.5176 (2.5.5) vs 3.5541 (2.4.6)**, exactly the stored value, so the 0.036 shift is one extra point in the max.
- **Validation of the proxy.** Re-running the whole REPRO_CHECK 9b cell (70 rows, 10 datasets, 7 estimators) under numpy 2.4.6 gives **MATCH_EXACT: 70/70 rows, every non-timing value bit-identical** (the 2.5.5 run had 51 E7 values differing by > 1e-6). So the stored 9b results are consistent with numpy 2.4.6 walks; this does not prove host-T ran 2.4.6.
- **Scope (sample, not exhaustive; Addendum B).** Sampling only, datasets 0-29 of every cell, walks compared between 2.4.6 and 2.5.5: groups b32 and b8, 960 datasets each. Walks differ in **628/960 (b32) and 567/960 (b8)** datasets, in 22 of 32 cells in each group (in the 30 sampled datasets per cell, the small cells never differ: torus2 L=24, torus3 L<=24, 3D crossovers L<=112, aniso2 L=128; the larger cells, rings and 2D anisotropic cells mostly do); the first difference is usually in the last few grid points (first differing point counted from the end: 0-2 in about 1/3 of cases, rarely before 10). A crude proxy for window-based estimators (first differing index inside the exact-window length): 325/960 (b32), 276/960 (b8); 0 for torus3. b128 and the 200-dataset exhaustive scan were not run (host-D was at load ~25; the first attempt was abandoned unread, see Addendum B).
- **Which reported numbers it affects.** Not a bug, so no reported number is wrong. It is a platform-dependent walk realisation: (i) any bit-level comparison of E7/E7j/E8 (which use every grid point, so they are the most exposed) across environments, as in REPRO_CHECK 9b; (ii) the 10b regeneration in a second environment (paper Table VI; 278 windows changed); (iii) estimators whose window reaches a differing point. ## 2. Gemini 7.2 / 3: E4o in-sample covariance (Markowitz bias)
Ring L=512 (cell 2, wpn 32, E4o, M exact; 0 datasets with |b|>B in every arm). Replay seeds, 200 datasets; V0 reproduces the stored E4o rows exactly (200/200 abstain, J, coverage, hw within 1e-6; 177/200). Extra fresh-seed arm 1000 datasets (seeds `[22,13002,ds]`) because 200 datasets only give coverage to about +-3 points.

| variant | replay n=200: coverage (CP) | sd ratio | fresh n=1000: coverage (CP) | sd ratio | stoch.-part cov (200 / 1000) | mean crit |
|---|---|---|---|---|---|---|
| V0 baseline (S, crit: 200 draws, same half B) | 177/200 = 88.5% (83.2-92.6) | 0.868 (pooled 0.852) | 911/1000 = 91.1% (89.2-92.8) | 0.867 (0.857) | 83.5 / 87.0% | 2.49 |
| V1 B=1000 draws (S and crit, same half B) | 181/200 = 90.5% (85.6-94.2) | 0.900 (0.889) | 932/1000 = 93.2% (91.5-94.7) | 0.902 (0.894) | 86.5 / 89.6% | 2.51 |
| V2 S (weights, sd) from independent half A, 200 draws; crit from half-B draws | 191/200 = 95.5% (91.6-97.9) | 0.833 (0.836) | 960/1000 = 96.0% (94.6-97.1) | 0.864 (0.849) | 95.0 / 94.0% | 2.98 |

(sd ratio = median bootstrap sd_j / empirical sd of the stochastic part n_j across datasets within J strata, as in the earlier diagnosis; pooled = 1/std(n_j/sd_j).)
**Reading.** The referee's prediction (sd ratio rises to about 1.00 and coverage to about 95%) is half supported. Coverage does recover with an independent covariance split (96.0%, CP 94.6-97.1, fresh; 95.5% replay) and rises partly with B=1000 (93.2%). But the sd ratio does NOT go to 1: it is 0.86 with the independent split, the same as the baseline. What changes is the critical value (2.49 -> 2.98): with the same 200 draws used to choose the weights AND to calibrate the max-t, the in-sample draws make the normalised deviations look smaller (the Markowitz/in-sample effect shows up in `crit`), while the remaining shortfall in the sd itself is not caused by in-sample weight choice. B=1000 helps by reducing noise in S, not by removing the in-sample use. This is a post-hoc diagnostic on one cell. V2 takes the covariance from the other half of the data (the weights are then independent of the half-B noise), but it is a different estimator, so a pre-registered amendment would be needed before it is called a fix. Not claimed: any change to E4c/E4r, other cells, or the earlier verdict that E4o fails C on this cell.
